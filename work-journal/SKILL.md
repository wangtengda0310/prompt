# 工作记录与报告生成

## 文件位置约定

| 类型 | 路径模板 | 示例 |
|------|----------|------|
| 每日纪要 | `d:\work\工作内容-{YYYY-MM-DD}.md` | `d:\work\工作内容-2026-04-01.md` |
| 晨会报告 | `d:\work\报告\晨会-{YYYY-MM-DD}.md` | `d:\work\报告\晨会-2026-04-01.md` |
| 周报 | `d:\work\报告\周报-{YYYY}W{WW}.md` | `d:\work\报告\周报-2026W14.md` |
| 月报 | `d:\work\报告\月报-{YYYY-MM}.md` | `d:\work\报告\月报-2026-04.md` |

如果 `d:\work\报告\` 目录不存在，自动创建。

## 模式零：自动记录（核心机制）

自动记录是此技能最关键的功能，目的是在关键节点自动捕获工作内容，避免事后回忆遗漏。

### 为什么自动记录很重要

事后统记工作容易出现两种问题：一是忘记做了什么（尤其是琐碎的小任务），二是遗漏上下文（为什么做、关联了什么）。自动记录通过在关键动作发生的瞬间捕获信息来解决这个问题。

### 自动记录节点与行为

#### 节点 1：git 提交成功后

这是最高价值的自动记录点。每次成功执行 `git commit` 后，立即将提交信息追加到当天纪要文件。

**操作步骤**：
1. 检测到 git commit 命令执行成功（通过输出中包含提交 hash 判断）
2. 获取提交详情：`git log -1 --format="%h %s"`
3. 判断提交属于哪个模块（主仓库还是子模块）
4. 追加到 `d:\work\工作内容-{今天日期}.md`

**追加格式**（追加到"备注"章节之前）：
```markdown
### {从 commit message 推断的任务标题}

**提交**: `{short_hash} {commit_message}`
**模块**: {模块名}
**时间**: {HH:MM}
```

**去重规则**：追加前检查文件中是否已包含该 commit hash，已存在则跳过。

#### 节点 2：制定计划时

当使用 ExitPlanMode 完成计划制定并获得用户批准后，记录计划摘要。

**追加格式**：
```markdown
### 制定计划: {计划标题}

**背景**: {用户原始需求的一句话概括}
**状态**: 计划已批准，待实施
**时间**: {HH:MM}
```

#### 节点 3：完成重要任务时

当完成一个非平凡的任务（非简单问答、非纯搜索）时，主动记录。

判断标准：如果任务涉及修改代码、创建文件、或执行多步骤操作，就值得记录。

**追加格式**：
```markdown
### {任务标题}

**内容**: {一句话说明做了什么}
**涉及文件**: {列出主要修改的文件}
**时间**: {HH:MM}
```

#### 节点 4：会话开始时

当新会话启动时，检查当天纪要文件是否存在。
- 如果不存在：不创建空文件，等有实际工作内容时再创建
- 如果已存在：不需要额外操作

此节点不写入内容，仅做状态检查。

### 自动记录的执行方式

自动记录通过 Claude Code 的 hooks 系统实现，配置在 `.claude/settings.local.json` 中：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "bash .claude/skills/work-journal/scripts/record-commit.sh",
            "timeout": 5000
          }
        ]
      }
    ]
  }
}
```

hook 脚本负责在 git commit 后自动追加记录。计划制定和任务完成的记录由 Claude 在对话中主动执行。

### 自动记录 vs 手动记录

| 维度 | 自动记录 | 手动记录 |
|------|----------|----------|
| 触发 | 关键节点自动触发 | 用户主动请求 |
| 内容粒度 | 精简（提交 hash + 一句话） | 详细（背景 + 实施内容 + 提交） |
| 目的 | 防止遗漏 | 完整记录 |
| 关系 | 自动记录的内容在手动记录时会被整合，不会重复 |

手动记录时，应检查自动记录的内容并将其整合进正式纪要中，避免重复条目。

## 模式一：记录每日工作

### 触发条件
用户要求记录当天或某天的工作。默认记录当天。

### 数据来源（按优先级）
1. **当前对话上下文** — 本次对话中完成的任务（最主要的来源）
2. **已有纪要文件** — 检查 `d:\work\工作内容-{日期}.md` 是否已有自动记录的内容，如有则整合
3. **git 提交记录** — `git log --since="YYYY-MM-DD 00:00:00" --until="YYYY-MM-DD 23:59:59" --all --oneline`（在主仓库和各子模块中分别执行），用于补充对话上下文中未覆盖的工作
4. **历史对话回顾** — 读取 `~/.claude/history.jsonl` 获取该日期的用户输入，还原工作上下文（详见下方"历史对话回顾"章节）
5. **用户的口头描述** — 如果以上信息不足，主动询问用户今天做了什么

### 回顾机制

当用户询问过去某天/某段时间的工作内容时（如"前天做了什么"、"上周的工作"），必须按以下优先级查找：

1. **先读取对应日期的纪要文件** — 这是最完整的一手记录
2. **再查 git 提交记录** — 作为补充，可能捕获到纪要中遗漏的提交
3. **读取历史对话记录** — 从 `~/.claude/history.jsonl` 提取该日期的所有用户输入
4. **必要时唤醒历史会话** — 使用 `claude -p` 配合 `--resume` 查询历史会话（见下方）
5. **交叉验证** — 纪要中提到但 git 中没有对应提交的，说明是讨论/分析类工作；git 中有提交但纪要没提到的，补充进回答
6. **如果纪要文件不存在** — 完全依赖 git log + history.jsonl + 历史会话 提取信息

### 历史对话回顾

这是一个强大的补充能力，可以还原纪要文件缺失或 git 提交未覆盖的工作内容。

**重要：不要直接读取 `~/.claude/history.jsonl` 文件**，该文件可能超过 1000 行，会导致 token 膨胀。使用下方提供的脚本或 subagent 处理。

#### 第一层：轻量回顾（通过脚本过滤）

使用 `history-summary.py` 脚本按日期过滤，只返回目标日期的条目：

```bash
# 今天
python ~/.claude/skills/work-journal/scripts/history-summary.py

# 指定日期
python ~/.claude/skills/work-journal/scripts/history-summary.py --date 2026-03-31

# 日期范围
python ~/.claude/skills/work-journal/scripts/history-summary.py --from 2026-03-25 --to 2026-03-31

# 本周/本月
python ~/.claude/skills/work-journal/scripts/history-summary.py --week
python ~/.claude/skills/work-journal/scripts/history-summary.py --month
```

脚本输出格式：`HH:MM | 项目名 | 用户输入（截断到80字符）`

这种方式零额外 token 消耗（相比直接读整个文件），但只能看到用户的提问，无法看到 Claude 的回复和实际操作。

#### 第二层：深度回顾（通过 subagent 唤醒历史会话）

当轻量回顾信息不足时，**使用 subagent 执行深度回顾**，避免主会话 context 膨胀：

```
启动一个 subagent，任务：
1. 运行 python ~/.claude/skills/work-journal/scripts/history-summary.py --date {目标日期} 获取该日期的会话列表
2. 找到消息数较多的 session-id（这些通常包含更多实际工作）
3. 对每个重要会话运行：
   claude -p "请用3-5句话总结本次会话中完成了哪些工作" --resume <session-id>
4. 汇总所有会话摘要，返回一段简洁的工作内容描述（不超过500字）
```

**Windows 环境注意事项**：
- `claude -p --resume` 在 Git Bash 中运行时，需要确保 `CLAUDE_CODE_GIT_BASH_PATH` 环境变量已设置
- 本机正确路径：`C:\Users\v-wangtengda\AppData\Local\Programs\Git\bin\bash.exe`
- 如果 subagent 执行 `claude -p` 报错找不到 bash，先运行：
  `export CLAUDE_CODE_GIT_BASH_PATH="C:\\Users\\v-wangtengda\\AppData\\Local\\Programs\\Git\\bin\\bash.exe"`

**注意事项**：
- 深度回顾消耗 API token，应谨慎使用
- 优先使用第一层脚本 + git log，信息不足时才用 subagent
- 每个会话只需查询一次
- subagent 返回的摘要应控制在 500 字以内，避免主会话 context 膨胀

#### 适用场景判断

| 信息充分度 | 推荐方式 |
|-----------|---------|
| 有纪要文件 | 直接读取纪要，不需要历史回顾 |
| 无纪要，git log 足够 | git log + 脚本轻量回顾 |
| 无纪要，git log 不够 | subagent 深度回顾 |

### 纪要格式

```markdown
# {YYYY-MM-DD} 工作纪要

## 完成任务

### {任务标题}

**背景**: {为什么做这件事，一句话说明}

**实施内容**:
1. {步骤1}
2. {步骤2}
...

**提交**: `{commit_hash} {commit_message}`

---

### {另一个任务}
...

## {子模块名} 子模块更新

**{分类}**:
- `{commit_hash} {type}: {description}`
...

---

## 备注

- {补充说明}
...
```

### 写入规则
- 如果文件已存在，**追加**新内容而非覆盖。检查已有内容避免重复
- 如果文件不存在，创建新文件
- 每个任务单独一个 `###` 章节
- git 提交记录按子模块分组，每个子模块下按类型（feat/fix/refactor/docs/test/chore）分类
- 提交 hash 和消息从 `git log` 获取，不要编造
- **如果当天没有 git 提交也没有对话中的工作内容**，提示用户"今天似乎没有记录到工作内容，请告诉我你今天做了什么"

## 模式二：生成报告

根据用户请求的类型生成对应报告。如果用户没有明确指定类型，根据当前日期推断：
- 周一、三、五 → 晨会报告
- 周五或周末 → 周报
- 月末最后一天或月初第一天 → 月报

### 晨会报告

**时间范围**：上一次晨会日到今天（通常覆盖 1-2 天的工作纪要）
**晨会日**：每周一、三、五

**输出格式**：
```markdown
# 晨会报告 {YYYY-MM-DD}

## 昨日/近期完成

- {简要描述1}（{涉及模块}）
- {简要描述2}（{涉及模块}）
...

## 进行中/待处理

- {从工作内容推断的未完成事项}
...

## 需要协调

- {跨模块或需要他人配合的事项，没有则写"无"}
```

**要点**：
- 控制在 5-10 条以内，晨会讲究简洁
- 每条一行，不要展开细节
- 侧重"做了什么"而非"怎么做"

### 周报

**时间范围**：本周一到本周五（或当前日期）

**输出格式**：
```markdown
# 周报 {YYYY-MM-DD} ~ {YYYY-MM-DD}

## 本周工作总结

### {工作类别1}
- {具体事项1}：{简要说明}
- {具体事项2}：{简要说明}

### {工作类别2}
- ...

## 本周提交统计

| 模块 | 提交数 | 主要变更 |
|------|--------|----------|
| {模块1} | {N} | {关键词} |
| ... | ... | ... |

## 下周计划

- {基于当前工作推断或留空让用户填写}
...

## 风险与问题

- {遇到的阻塞或风险，没有则写"无"}
```

**要点**：
- 按工作类别分组（功能开发、bug修复、重构、文档、子模块维护等）
- 不需要列出每个提交，按类别归纳
- 统计数据从 git log 中提取，要准确

### 月报

**时间范围**：本月 1 日到月末（或当前日期）

**输出格式**：
```markdown
# 月报 {YYYY年M月}

## 本月工作概览

{一段话总结本月重点工作方向和成果}

## 各周工作回顾

### 第1周 ({MM.DD} ~ {MM.DD})
- {本周重点1}
- {本周重点2}

### 第2周 ({MM.DD} ~ {MM.DD})
- ...

### 第3周 ...
### 第4周 ...

## 本月关键成果

1. **{成果1}**：{说明}
2. **{成果2}**：{说明}
...

## 本月统计

| 指标 | 数值 |
|------|------|
| 工作天数 | {从纪要文件数推断} |
| 总提交数 | {从 git log 统计} |
| 涉及模块 | {列出} |
| 新增功能 | {feat 提交数} |
| Bug修复 | {fix 提交数} |
| 代码重构 | {refactor 提交数} |

## 下月计划

- {基于工作趋势推断或留空让用户填写}
```

**要点**：
- 月报要有高度概括性，不要罗列每个提交
- "关键成果"强调业务价值而非技术细节
- 统计数据要覆盖主仓库和所有子模块

## 模式三：定时提醒

### 定时规则

| 报告类型 | 触发时间 | Cron 表达式 |
|----------|----------|-------------|
| 晨会提醒 | 周一、三、五 9:30 | `30 9 * * 1,3,5` |
| 周报提醒 | 周五 17:30 | `30 17 * * 5` |
| 月报提醒 | 每月最后一天 17:00 | 见下方说明 |

月报的 cron 无法直接表达"每月最后一天"，使用每天 17:00 检查的方式或在每月 28 日触发。

### 提醒内容

提醒时应：
1. 告知用户需要生成报告
2. 询问用户是否现在生成
3. 如果用户同意，立即执行对应的报告生成流程

### 定时任务的持久化

使用 `CronCreate` 的 `durable: true` 模式，确保定时任务在 Claude Code 重启后仍然有效。

## 通用规则

1. **日期处理**：所有日期使用 `YYYY-MM-DD` 格式，使用当天实际日期（从系统获取）
2. **周数计算**：使用 ISO 周数，`WW` 为两位数（如 `14`）
3. **git 命令**：在执行 git log 时，需要在主仓库和每个子模块目录中分别执行，汇总结果
4. **文件编码**：所有文件使用 UTF-8 编码
5. **避免重复**：生成报告前检查是否已存在同一天的报告文件，如果存在询问用户是否覆盖
6. **信息不足时**：如果工作纪要文件不足以生成报告，主动从 git log 补充信息，仍然不够则询问用户
